# Notification Center V1

## Scope

Notification Center V1 is a persisted, user-specific in-app inbox generated from Watchlist V2 alert objects.

It is not a background push service.

- no device push-token registration
- no operating-system notification permission
- no scheduled worker or cron claim
- no delivery while the application is closed
- no client-authored notification title or message
- no paper stake or real-money action

The user starts synchronization from the web or native Watchlist/Notification Center interface.

## Data path

```text
Authenticated user
  -> own Watchlist rows through RLS
  -> current server Top Picks
  -> deterministic Watchlist alert engine
  -> notification candidate engine
  -> own Notification Center rows through RLS
```

The client may request synchronization, but it cannot provide an alert type, severity, title, message, event state or calculated price movement.

## Structured rows

A stored notification contains only bounded structured fields:

- server-generated source key
- source type
- notification type
- severity
- related Watchlist and event identifiers
- match and selection labels
- scheduled start when available
- bounded calculated payload
- first and latest observation timestamps
- read timestamp
- dismissed timestamp

The interface renders localized Finnish, English or Spanish text from the notification type and payload.

## Supported types

- `kickoff_soon`
- `decision_changed`
- `price_moved`
- `below_play_price`
- `market_unavailable`
- `fixture_passed`

## Deduplication

Every row uses a unique `(user_id, source_key)` index.

The source key is created from server-owned identifiers and a bounded state fingerprint:

- kickoff notifications use broad time windows
- decision notifications use the old and current decision
- price notifications use direction and threshold-multiple buckets
- PLAY-floor notifications use bounded gap buckets
- unavailable and expired states use a stable state key

This avoids creating a new row for every small price change while allowing a materially stronger price movement or a different decision state to appear as a new notification.

Dismissal stores `dismissed_at` rather than deleting the deduplication key. A continuing identical state therefore remains dismissed after the next synchronization.

## Preferences

Each user may configure:

- Notification Center enabled or disabled
- minimum severity: info, medium or high
- kickoff notifications
- price and PLAY-floor notifications
- decision-change notifications
- unavailable-market and expired-watch notifications

Preferences affect future synchronization. Existing visible rows remain available until read or dismissed.

## Security controls

- validated cookie or mobile bearer session
- exact-origin validation for cookie mutations
- per-user read, write and sync quotas
- forced RLS on notification rows and preferences
- every query also filters by the authenticated user ID
- maximum 50 generated candidates per synchronization
- maximum 200 retained inbox rows per user
- bounded structured payload generated by the server
- no service-role key in the client or Notification Center API
- account export and deletion coverage

## Privacy behavior

Notification Center stores no email content, contact data, precise location, payment data, bookmaker credentials or real-money balance.

Account export includes notification preferences and notification history, including dismissed rows. Account deletion removes both tables before deleting the authentication account.

## Activation

Run after Watchlist V2:

```text
supabase/scorecaster_notification_center.sql
```

Then execute the Notification Center cases in `docs/AUTH_CLOUD_SETUP.md`, including account A/account B isolation and both web-cookie and mobile-bearer sessions.

## Future push phase

A future push phase requires a separate reviewed design covering:

- explicit user permission
- protected device-token lifecycle
- token rotation and deletion
- server-owned scheduling
- duplicate delivery controls
- provider credentials
- delivery receipts and failure handling
- App Store and Google Play disclosure updates
- real-device security and privacy testing

Notification Center V1 must not be described as push-enabled until that phase is implemented and verified.
